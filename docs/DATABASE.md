# База данных

Схема PostgreSQL реализована четырьмя [миграциями Goose](../backend/migrations/) по [§5 ТЗ](../SPECIFICATION.md#5-модель-данных-и-postgresql).

| Таблица | Связи и ограничения |
| --- | --- |
| `users` | UUID, имя, уникальный нормализованный email, Argon2id PHC-хеш, timestamps |
| `tasks` | Владелец из `users`, длины заголовка и описания, статус, позиция, nullable due date и soft delete |
| `refresh_tokens` | Владелец из `users`, уникальный SHA-256 хеш в lowercase hex, абсолютный срок действия и время отзыва |
| `task_history` | Задача из `tasks`, предыдущий и новый статус, время события, не более одной первоначальной записи на задачу |

Допустимые статусы — `not_started`, `in_progress`, `finish` и `done`. Finish означает выполненную работу, Done — сданную и закрытую задачу. Для активной задачи позиция целочисленная и неотрицательная. Уникальность пары «владелец и статус» с позицией проверяется при commit, поэтому обмен позициями возможен в транзакции. Плотность позиций и запись истории вместе с переходом обеспечивает сервис задач.

Сначала все операции записи задач выполняют `SELECT ... FOR UPDATE` по владельцу. Все последующие запросы к активной задаче фильтруют по ID, владельцу и `deleted_at IS NULL`. Create и смена статуса через обычный PATCH используют длину целевой колонки как индекс добавления. При перемещении обновляются затронутые диапазоны. Ошибка commit при нарушении deferred-ограничения откатывает и порядок, и историю.

Дедлайн хранится как `DATE`, события как `TIMESTAMPTZ`. При soft delete `deleted_at` получает значение, `position` сбрасывается в NULL, история сохраняется. Физическое удаление аккаунта каскадно очищает задачи, их историю и токены. Индексы покрывают активную доску, сроки и владельцев токенов и историю задачи, включая выборку событий Done.

Начальная запись истории имеет `old_status = NULL`. Фактические переходы дописываются при PATCH и move, включая повторные попадания в Done. Редактирование остальных полей, сортировка и soft delete историю статусов не меняют. Для событий используется время выполнения записи после блокировки владельца. Статистика ищет первое Done по всей истории, включая удалённые задачи.

## Запрос Statistics и план выполнения

Запрос фильтрует `tasks` по `user_id` и использует `LATERAL` с `ORDER BY changed_at LIMIT 1` для событий Done каждой задачи. Это эквивалент MIN по полной истории. Только после выбора первого события применяются текущий момент, самая ранняя запрошенная граница и полуоткрытые интервалы. Один statement накапливает счётчики для buckets, недели и месяца.

Локальный `EXPLAIN (ANALYZE, BUFFERS)` выполнен в изолированной схеме PostgreSQL 18.4 (Debian trixie, Docker, Linux x86_64, Intel Core i7-12700H). Три запуска использовали режим Weeks с 10 диапазонами UTC, один аккаунт с 250 задачами и набор из 80 владельцев, 20 000 задач (4 000 soft-deleted), 108 000 событий и 24 000 событий Done. У 60% задач было по два перехода в Done. Перед измерением выполнен `ANALYZE`.

| Наблюдение | Результат |
| --- | --- |
| Поиск задач владельца | Bitmap Index Scan по `tasks_owner_status_position_key` |
| Поиск первого Done | Index Only Scan по частичному `task_history_done_idx` под `Limit`, 250 обращений для 250 задач, 150 проверок heap на свежих данных |
| Буферы выполнения | 659 попаданий в shared buffers на запрос |
| Время выполнения | 3,276 мс на первом запуске, 1,462 мс и 1,215 мс на следующих |
| Время планирования | 1,669 мс, 0,623 мс и 0,549 мс |

План использует существующие индексы. Измерение характеризует локальный тестовый набор с прогретыми вставками, время HTTP и production-нагрузка в него не входят.

## Сессии

Существующие таблицы используются без изменения схемы. В `users.password_hash` хранится PHC Argon2id. В `refresh_tokens.token_hash` хранится lowercase hex SHA-256 от 32 случайных байт. При ротации `expires_at` копируется из старой записи. Отозванные записи остаются доступными для отказа при повторном использовании. Автоматическая очистка на этапе 2 не выполняется. Просроченные записи можно удалять отдельной операцией обслуживания, когда они больше не нужны для учёта сессий.

## Миграции

При `docker compose up --build -d` одноразовый сервис `migrate` применяет недостающие Up и завершает работу. Версии хранятся в `goose_db_version`. Конкурирующие запуски сериализуются PostgreSQL advisory lock.

```sh
docker compose run --rm migrate /usr/local/bin/migrate status
docker compose run --rm migrate
```

Второй вызов при актуальной схеме завершается с `applied: 0`. Команда `go run ./cmd/migrate down` из `backend` откатывает одну миграцию. Она удаляет таблицу последней версии и применяется в тестах только к отдельной БД. Интеграционный тест разворачивает собственную временную схему в `focusboard_test`, выполняет Up → Down до версии 0 → Up и удаляет тестовую схему. Применённые миграции сохраняются, исправления оформляются следующими версиями.

## Резервное копирование

Из корня проекта для запущенного Compose:

```sh
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > focusboard.dump
```

Для проверки восстановления создай чистую отдельную базу. Например, подключись к контейнеру командой `docker compose exec db sh`, создай базу командой `createdb -U "$POSTGRES_USER" focusboard_restore_test`, а из хоста выполни:

```sh
docker compose exec -T db sh -c 'pg_restore --exit-on-error -U "$POSTGRES_USER" -d focusboard_restore_test' < focusboard.dump
```

Команда `docker compose down` оставляет именованный том. Флаг `-v` удаляет том и его данные. Перед production-миграциями требуется резервная копия.
