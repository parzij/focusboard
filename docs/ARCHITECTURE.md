# Архитектура

Проект состоит из Go API и React SPA в одном репозитории. Утверждённые границы описаны в [§3 ТЗ](../SPECIFICATION.md#3-архитектура).

## HTTP и PostgreSQL

- `backend/cmd/api` загружает и валидирует конфигурацию из окружения, настраивает JSON-логи slog и собирает HTTP-сервер на Chi. В журнал запроса попадают ID, метод, шаблон маршрута, статус и длительность.
- `internal/platform/postgres` настраивает один pgxpool на процесс. Проверка `Ping` получает контекст запроса и ограничена `DB_CHECK_TIMEOUT`. При недоступности БД HTTP-сервер остаётся живым, readiness восстанавливается с подключением пула. При SIGINT или SIGTERM сервер завершает активные запросы в пределах таймаута и закрывает пул.
- `internal/httpx` преобразует результат проверки в HTTP-ответ. Бизнес-модули используют Handler → Service → Repository. Пробы проверяют инфраструктуру напрямую через переданную функцию.
- `backend/cmd/migrate` запускает Goose со встроенными SQL-файлами. Compose дожидается healthcheck PostgreSQL и успешного выхода контейнера миграций перед запуском API.
- React/Vite в `frontend` запускается отдельно.

## Authentication и Users

`cmd/api` передаёт конфигурацию и общий pgxpool в `internal/app`. Модуль `internal/auth` владеет регистрацией, проверкой затребованных credentials, выдачей и отзывом сессий, включая смену пароля. `internal/users` читает и обновляет публичный профиль. HTTP-слой декодирует JSON и отображает доменные ошибки. SQL с параметрами и транзакции находятся в репозиториях. Повторно используемый middleware `httpx.RequireBearer` помещает проверенный UUID из JWT в контекст.

Хеширование и проверка паролей выполняются в `internal/platform/password`, а подпись JWT и формирование refresh-значений — в `internal/platform/token`. Проверка Argon2id выполняется до захвата блокировки строки пользователя. Репозиторий login сверяет хеш под блокировкой. Refresh берёт ту же блокировку до отзыва и вставки. Смена пароля условно обновляет строку с проверенным старым хешем и отзывает сессии под этой блокировкой в одной транзакции.

## Tasks

`internal/app` подключает шесть маршрутов `internal/tasks` с существующим Bearer middleware и таймаутом запроса. `handler.go` разбирает HTTP и возвращает стандартные ошибки. `dto.go` описывает JSON, включая наличие поля при PATCH. `task.go` содержит доменные типы, правила значений и ошибки, `service.go` управляет операциями, а `repository.go` выполняет SQL с параметрами.

Записи используют PostgreSQL Read Committed. Сначала транзакция блокирует строку владельца, затем читает и меняет задачи. Это тот же порядок, который используют операции Authentication с блокировкой пользователя. Обновление профиля тоже конфликтует с блокировкой его строки. Независимые доски блокируют разные строки. Конкурентный PATCH читает актуальную запись под блокировкой и изменяет переданные поля. Чтение доски получает согласованный снимок одним SQL-запросом.

Move проверяет плотность исходной и целевой колонок по количеству и максимальной позиции. В одной колонке сдвигается только диапазон между старым и новым индексами. Между колонками хвост исходной колонки сдвигается влево, а часть целевой от индекса вставки вправо. Доска читается под той же блокировкой и возвращается после успешного commit. История добавляется в транзакции изменения задачи.

## Statistics

`internal/statistics` обслуживает `GET /api/v1/statistics` через общий pgxpool, Bearer middleware и таймаут HTTP. Handler проверяет query, DTO задаёт публичный формат, Service читает внедрённые часы один раз, строит локальный календарь и заполняет отсутствующие значения нулями. Repository возвращает только агрегаты одним SQL statement на одном MVCC-снимке.

Go преобразует календарные диапазоны в полуоткрытые UTC-интервалы, разбивая их в точках смены UTC offset. Такой расчёт покрывает повторяющееся и пропущенное локальное время, включая переходы в полночь. PostgreSQL сравнивает готовые `TIMESTAMPTZ`, используя тот же момент отсечения для всех полей. Образ API уже включает IANA tzdata из стадии сборки.

## Целевая архитектура

Caddy отдаёт статику Vite с SPA fallback и сохраняет префикс `/api/v1` при проксировании в Go. Браузер обращается к API с того же origin. PostgreSQL доступна API и одноразовому заданию Goose.

Backend состоит из модулей auth, users, tasks и statistics. Middleware устанавливает проверенный user ID, Handler обрабатывает HTTP, Service реализует правила и транзакции, Repository выполняет параметризованный SQL. Statistics читает историю задач. Конструкторы принимают явные зависимости.

На фронтенде `pages` собирает экраны из `features` и `entities`; `shared` содержит общие UI-компоненты, стили и API client. TanStack Query управляет серверными данными. Access token живёт в памяти, восстановление сессии проходит через refresh cookie.
