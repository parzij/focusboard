# Архитектурные решения

## Минимальный стартовый срез

Этап 0 добавляет реальные точки входа Go/Chi и React/Vite. Папки модулей появляются с первым кодом. Это сохраняет связь структуры с реализацией и делает каркас проверяемым без БД и прикладного API.

## Управление зависимостями

Go modules фиксируют Chi и контрольные суммы. pnpm из `frontend/package.json` и `frontend/pnpm-lock.yaml` фиксирует клиентское дерево. Выбран Go 1.27 и Node.js 26. Новые зависимости подключаются вместе с использующим их кодом или проверками.

## Проверки фронтенда

ESLint использует рекомендованные правила JavaScript и TypeScript, Prettier проверяет форматирование файлов фронтенда. Файл `pnpm-lock.yaml` проверяется отдельной установкой с `--frozen-lockfile`.

## PostgreSQL и миграции

API использует pgxpool и остаётся доступен для liveness при потере БД. Readiness ограничен отдельным таймаутом. Compose запускает API после Goose. Миграции встроены в отдельную команду, сериализуются advisory lock PostgreSQL и выполняются транзакционно.

Позиция уникальна в границах владельца и статуса. Отложенная проверка уникальности позволяет менять порядок несколькими SQL-командами в транзакции. Хеш refresh-токена хранится как 64 строчных шестнадцатеричных символа SHA-256. БД проверяет форму PHC для Argon2id, а параметры и подлинность будет проверять код авторизации.

## Authentication

- JWT подписывается HS256. Ключ генерируется вне приложения. Конфигурация проверяет канонический Base64 и размер, а также отбрасывает очевидно вырожденные значения. Случайность ключа обеспечивается генератором.
- Argon2id использует 64 МиБ, time cost 3 и parallelism 1. Соль 16 байт, результат 32 байта. Верификатор принимает этот профиль. Отсутствующий аккаунт и повреждённый хеш используют dummy-проверку. Достигнув лимита одновременных вычислений, сервер возвращает 429. Локальный benchmark на Intel Core i7-12700H, Linux/amd64, 8 итераций показал 268 мс и 67,1 МБ аллокаций на хеш. Измерение в целевом production-окружении относится к подготовке релиза.
- Login, refresh и смена пароля используют блокировку строки пользователя. Login сверяет хеш под блокировкой. Ошибка вставки откатывает отзыв старого refresh-токена. При повторном использовании отозванного токена новый запрос получает 401, а действующая сессия-потомок сохраняется.
- Rate limiter работает на процесс, ограничивает число ключей и очищает их при смене окна. IPv4 группируется по адресу, IPv6 по /64. Заголовки прокси игнорируются. При подключении Caddy нужно настроить доверенную цепочку, иначе лимит будет учитывать адрес прокси.

## Порядок задач и конкуренция

- Create, Update, Move и Delete используют блокировку строки владельца в PostgreSQL. Блокировка берётся первой, операции разных владельцев используют разные строки. Это позволяет читать свежую версию задачи для частичного PATCH.
- Позиции хранятся плотными. Move использует индекс вставки после удаления перемещаемой карточки из исходного списка и изменяет только затронутые диапазоны. Успешный снимок доски читается внутри транзакции и отправляется после commit.
- Выход индекса за допустимый диапазон возвращает 422. Обнаруженный разрыв в проверяемой колонке или конфликт существующего deferred-ограничения возвращает 409 `ORDER_CONFLICT`. Допустимый индекс интерпретируется в текущей колонке. Версия доски в API отсутствует.
- Переходы записываются вместе с изменениями задачи. История хранит все фактические переходы в Done и сохраняется после soft delete. Текущих миграций достаточно.

## Календарная статистика

- `period` по умолчанию равен `days`, `timezone` равен `UTC`. Явно пустые, неизвестные и повторяющиеся параметры возвращают 422. Разбор IANA выполняется в Go с исключением системных имён и путей.
- Go рассчитывает границы по одной отметке времени, учитывая смены UTC offset. PostgreSQL получает готовые полуоткрытые UTC-интервалы и считает все показатели одним statement. Версия timezone data PostgreSQL на результат не влияет.
- Первое Done выбирается через упорядоченный поиск по существующему частичному индексу для каждой задачи владельца. Срез по времени применяется после поиска. Подробности и измерения приведены в [документации БД](DATABASE.md#запрос-statistics-и-план-выполнения).

## SPA и координация сессии

- В браузере все запросы идут на origin Vite, который сохраняет префикс и Origin при проксировании в Go. Локальные команды используют `127.0.0.1` и строгий порт 5173.
- Single-flight refresh переиспользуется в StrictMode и при параллельных ответах 401. Web Locks последовательно выполняет операции, меняющие общую cookie, между открытыми вкладками. BroadcastChannel передаёт только сигналы входа и выхода. При отсутствии Web Locks очередь действует в пределах одной вкладки. При отсутствии BroadcastChannel соседняя вкладка обнаруживает смену сессии при следующей проверке.
- Сетевой сбой сохраняет возможность повторить проверку сессии или logout. При подтверждённой смене сессии отменяются запросы и очищается QueryClient. Access JWT хранится в памяти.
- Playwright запускается на изолированной PostgreSQL через Compose. Диагностические изображения маскируют поля и приватные данные. Запись сетевого trace для сценариев с credentials не используется.
