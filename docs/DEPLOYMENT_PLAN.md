# Предварительный план production deployment

Функциональный MVP принят. Аккаунт OCI, виртуальная машина и домен пока отсутствуют. `focusboard.ru` — предполагаемое имя. План не запускает инфраструктуру и не создаёт релиз.

1. **Хост.** После регистрации проверить домашний регион OCI, доступность Ampere A1 и маркировку Always Free для VM, IP и хранения перед созданием. Выбрать поддерживаемый Ubuntu Server ARM64, обновить ОС, создать непривилегированного оператора и настроить вход по SSH-ключам. Если доступной бесплатной ёмкости нет, отложить запуск и согласовать дальнейшие действия. [Oracle Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)
2. **Сеть.** Подготовить VCN, публичную подсеть и закреплённый IP после проверки стоимости. Ограничить SSH доверенными адресами или согласованным каналом доступа. В OCI NSG и на хосте разрешить публичные TCP 80/443 для Caddy. Проверить проброс Docker, чтобы правила host firewall не оказались обойдены опубликованным портом. Не публиковать 5432 и 8080.
3. **Сборка.** Установить Docker Engine и Compose v2. Проверить manifest для всех закреплённых образов Go, Debian, PostgreSQL, Node и будущего Caddy. Собрать backend и production React assets для `linux/arm64` через Buildx либо на ARM64 и запустить smoke на целевой архитектуре. Использовать проверенные образы по immutable digest. [Docker Buildx и multi-platform](https://docs.docker.com/build/building/multi-platform/)

   У текущих закреплённых образов Go 1.27.4, Debian trixie-slim и PostgreSQL 18.4 проверено наличие `linux/arm64` в manifests. Сборка и запуск на ARM64 остаются проверкой этапа 9.
4. **Сервисы.** Добавить production Compose и Caddy на этапе 9. Caddy отдаёт `dist` с SPA fallback и проксирует `/api/v1/` на Go в приватной сети. PostgreSQL использует постоянный том. Goose запускается как одноразовый сервис до смены версии API; ошибочная миграция блокирует запуск. Публичный proxy закрывает внутренние диагностические endpoints.
5. **DNS и TLS.** После покупки направить A-запись на подтверждённый адрес. AAAA включать только после проверки IPv6. Настроить hostname и постоянное хранилище сертификатов Caddy, проверить открытые 80/443, выпуск HTTPS, перенаправление HTTP и renew. [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
6. **Секреты.** Сгенерировать отдельный JWT secret и пароль БД. Хранить их вне Git в доступном только оператору файле окружения или согласованном хранилище. Установить production origin и Secure для refresh cookie. Ограничить права пользователя БД и automation. Для SSH согласовать public key и отпечаток хоста, закрытые ключи не передавать в чат.
7. **Backup и restore.** Сделать зашифрованный `pg_dump` перед миграциями, настроить расписание, срок хранения и копии вне VM в согласованном хранилище. Проверить восстановление на отдельной БД, миграции и вход. Проверить сценарий возвращения предыдущей версии без потери новых данных. Если откат образа несовместим со схемой, использовать проверенный план восстановления с согласованием потери записей после точки backup.
8. **CI/CD.** После успешного обычного CI собирать и проверять ARM64-образы. Развёртывать только проверенный digest через защищённое GitHub Environment с ручным подтверждением. Перед сменой версии проверить backup и миграции, после неё проверить readiness внутри сети, TLS и smoke для регистрации, сессий, доски и статистики. Хранить предыдущий digest и процедуру rollback.
9. **Приёмка.** Проверить конфигурацию firewall, SSH, доступность внутренних портов снаружи, cookie, Origin, rate limiting за proxy, изоляцию аккаунтов, уязвимости зависимостей, журналы без секретов, резервное восстановление и откат. Создавать тег v1.0.0 только после работающего production deployment и финальной приёмки владельцем.

## Что нужно от владельца

- Подтверждённый OCI аккаунт, домашний регион и compartment, выбранная бесплатная конфигурация и разрешение на создание конкретной VM.
- Подтверждение владения доменом, DNS-провайдер и согласованный набор записей. После создания VM — публичный адрес и, если нужен IPv6, подтверждение его маршрутизации.
- Ubuntu image, SSH username, публичный ключ, отпечаток хоста и доверенные IP для SSH. Секреты затем передаются через согласованное хранилище.
- Правила хранения backup, доступное хранилище без неподтверждённых расходов, допустимые простой и потеря данных при восстановлении, окно запуска и человек с правом подтвердить deployment.
