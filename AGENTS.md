# Инструкции для Codex

Перед изменениями прочитай [SPECIFICATION.md](SPECIFICATION.md) целиком, [README.md](README.md), [дорожную карту](docs/ROADMAP.md), актуальный код и относящиеся к работе [макеты](docs/mockups/). При расхождении приоритет у ТЗ. ТЗ и макеты изменяются только с согласия владельца. Дорожная карта фиксирует фактическое состояние этапов и ссылки на PR.

## Git Workflow

1. Проверь чистоту рабочего дерева. Переключись на `master` и выполни `git pull --ff-only origin master`.
2. Создай ветку текущего этапа от актуального `master` по [дорожной карте](docs/ROADMAP.md). Разработка ведётся в ветке этапа.
3. Реализуй этап небольшими шагами, добавляй тесты по мере разработки и запускай проверки каждого законченного блока.
4. Проверь весь diff, запусти применимые проверки и создай логические Conventional Commits с сообщениями на английском.
5. Перед каждым push проверь публикуемые коммиты на секреты и персональные данные. Отправь ветку и открой PR в `master` с англоязычным описанием изменений и фактическими результатами проверок.
6. Проверь все доступные статусы CI для текущего HEAD. Merge выполняется после успешных проверок и разрешения конфликтов, в рамках разрешения владельца. Падающие и незавершённые проверки блокируют merge.
7. Переключись на `master`, выполни `git pull --ff-only origin master` и удали завершённую feature-ветку локально и на GitHub, если она больше не нужна.
8. Подведи итог по-русски и переходи к следующему этапу по указанию владельца. Укажи цель, изменения, решения, файлы, команды, фактические результаты, ошибки, ветку, SHA, ссылку на PR, статус merge и состояние `master`.

Коммиты, push, PR, merge и удаление веток выполняй в рамках разрешения владельца. Force push в `master`, удаление `master`, переписывание опубликованной истории и обход проверок запрещены. Сохраняй чужие изменения. Для удаления данных, Docker volumes и production deploy требуется отдельное разрешение.

## Ручная визуальная приёмка

С этапа 5 для этапов с изменениями UI после успешных автоматизированных проверок запусти приложение локально, проверь реальные сценарии в браузере и подготовь скриншоты desktop и mobile. Передай владельцу точный loopback URL и команды запуска, открой PR и дождись успешного CI. Остановись перед merge до явной ручной визуальной приёмки владельца. Внеси согласованные исправления в ту же ветку, повтори тестирование и CI актуального HEAD и выполни merge после подтверждения владельца.

Согласуй перенос некритичных улучшений на следующие этапы. Изменение утверждённого дизайна требует согласия владельца.

## Стек и архитектура

- Go, Chi, pgx/pgxpool, параметризованный SQL, Goose, PostgreSQL, JWT access, refresh tokens, Argon2id, slog, REST/JSON, OpenAPI/Swagger и Go testing.
- React, TypeScript, Vite, React Router, Tailwind CSS, dnd-kit, TanStack Query, React Hook Form, Zod, Recharts, Lucide React, Inter, pnpm, Vitest, Playwright, ESLint и Prettier.
- Docker, Docker Compose, Caddy и GitHub Actions. Закрепляй версии и lockfiles. Изменения утверждённого стека и расширение границ MVP согласуй с владельцем.
- Модульный монолит. Handler разбирает HTTP и отображает ошибки, Service отвечает за сценарии и транзакции, Repository выполняет SQL. Доменные модели независимы от транспорта. Зависимости явные, сборка приложения в `backend/cmd/api`.
- SPA на одном origin с API. Страницы собирают features и entities, shared не зависит от страниц. TanStack Query отвечает за серверные данные. Состояние формы, модалки и drag хранится локально.
- Определяй владельца по проверенному JWT. Ограничивай им запросы к задачам, профилю и статистике. Храни access JWT в памяти, refresh cookie выдавай с HttpOnly, а в БД храни только хеш refresh token. Исключай секреты из Git, логов и клиентской сборки.

## Дизайн и качество

- UI, исходный код, commit messages и PR на английском. Документация и отчёты владельцу на русском.
- GitHub Dark, Inter, мягкие скругления, сдержанные бордеры и анимации. Единая страница `/auth` с горизонтальным переключением Sign in и Create account, включая мобильный режим и reduced motion.
- Единая конфигурация статусов. Not started `#8B949E`, In progress `#58A6FF`, Finish `#3FB950` для выполненной работы, Done `#BC8CFF` для сданной и закрытой задачи. Бордер карточки соответствует статусу.
- Реализуй только предусмотренные MVP элементы. Проверяй мобильный и десктопный UI в браузере, включая клавиатуру, фокус, контраст и touch.
- Применяй Go build, gofmt, vet, unit и интеграционные тесты PostgreSQL/Goose по мере появления компонентов. Добавляй проверки HTTP, токенов и изоляции аккаунтов. Для фронтенда используй typecheck, ESLint, Prettier, Vitest, production build и Playwright. Для DnD проверяй мышь, touch, клавиатуру и rollback. Для статистики проверяй timezone и первое Done. Проверяй Compose/Caddy после добавления инфраструктуры.
- Сохраняй тесты и валидацию. В отчёте различай успешные, упавшие, заблокированные и неприменимые проверки. При изменении контракта одновременно обновляй OpenAPI и профильную документацию. Существенные решения фиксируй в [DECISIONS.md](docs/DECISIONS.md).
